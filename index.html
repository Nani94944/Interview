01System Overview & Solution Map

What is TalentGateway?

Brassring TalentGateway is a mature enterprise recruitment platform built on .NET Framework 4.6.1. It uses a hybrid architecture: a firmly rooted N-Tier backend combined with a progressive frontend modernisation strategy that injects Angular 19 microfrontends into legacy ASP.NET MVC pages.

The system is split across multiple Visual Studio solutions, each responsible for a distinct concern. Communication between these solutions happens entirely at the HTTP/TCP boundary — they are never linked as shared library references.

02N-Tier Backend Architecture — Layer by Layer

Overview

The main application (TalentGatewayMVC.sln) is structured into four distinct tiers. Each layer has a single responsibility, strict dependency direction (upward layers depend on lower layers, never the reverse), and communicates with adjacent layers only — no layer skips another.

L1

Presentation Layer — TG.Web.UI

Path: TGNewUI\UserInterface\MVC\TG.Web.UI Tech: ASP.NET MVC 5.2.7 · Razor 3.2.7
  • Receives HTTP requests and routes them to the correct controller action
  • Renders Razor (.cshtml) views — the host page for both legacy AngularJS templates and modern Angular 19 Custom Elements
  • Manages user sessions and HTTP authentication cookies
  • Calls TG.Core services — never TG.Data directly
  • Returns HTTP responses: full HTML pages or JSON (via Web API controllers)
L2

Business / Infrastructure Layer — TG.Core

Path: TGNewUI\Infrastructure\TG.Core Tech: C# Class Library · .NET Framework 4.6.1
  • TG.Core.Utilities: CommonUtil.cs, RestClient.cs, TGEmailHelper.cs — cross-cutting helpers
  • TG.Core.Services: WcfServiceInvoker.cs and ChannelFactoryManager.cs — manage all outbound WCF calls
  • Cryptography: EncryptionManager.cs handles all data protection and key management
  • Logging: ILCEventLogger.cs and MSMQ-based loggers for audit trails
  • Contains no HTTP or UI concerns — purely business and infrastructure logic
L3

Data Access Layer — TG.Data

Path: TGNewUI\DataAccess\TG.Data Tech: ADO.NET · System.Data.SqlClient · Custom DatabaseHelper
  • DatabaseHelper.cs executes stored procedures and parameterised SQL queries
  • CommonDataUtil.cs handles data hydration — mapping raw SqlDataReader rows to C# objects
  • SessionRepository.cs manages state/session persistence in SQL
  • No ORM (Entity Framework not used here) — raw ADO.NET for performance and legacy compatibility
  • Returns mapped entity objects back to TG.Core — never surfaces raw DataReader to upper layers
L4

Service Contracts — TG.Services.Contracts

Path: TGNewUI\Services\TG.Services.Contracts Tech: C# Interface Library
  • Defines C# interfaces that decouple service callers from implementations
  • Both local (in-process) implementations and WCF remote proxies implement these interfaces
  • Allows swapping between local and remote service implementations without changing calling code
  • Referenced by TG.Core and TG.Web.UI — never by TG.Data
03Layer-to-Layer Communication: How Data Flows

A Request's Journey — End to End

Every user interaction follows the same vertical path through the layers. Below is a concrete walkthrough using a job search request as the example.

# From → To Mechanism What travels
1 Browser → TG.Web.UI HTTP GET/POST URL params, form body, session cookies
2 Controller → TG.Core C# method call Criteria/command object (e.g. JobSearchCriteria)
3 TG.Core → TG.Data C# method call Query parameters passed to repository interface
4 TG.Data → SQL Server ADO.NET SqlCommand Parameterised stored procedure call
5 SQL Server → TG.Data SqlDataReader Raw result set rows
6 TG.Data → TG.Core C# return value Mapped entity objects (e.g. List<JobEntity>)
7 TG.Core → TG.Web.UI C# return value DTO / domain result (e.g. JobSearchResultDto)
8 TG.Web.UI → Browser HTTP 200 response Rendered Razor HTML page or JSON payload

Strict Layer Ordering Rule

No layer may skip another. The Presentation layer (TG.Web.UI) never calls TG.Data directly. Data always travels back up through each layer in reverse order — each layer transforms and validates it before passing it up.

04Frontend Architecture & Frontend-to-Backend Communication

Three Frontend Generations

The frontend has three generations of UI technology living side by side in the same page, each with a different communication pattern with the backend.

Generation 1 — Legacy ASP.NET WebForms

The oldest screens live in KASTalentGateway.sln. These are ASP.NET WebForms (.aspx) pages. Communication is the classic PostBack model: the entire page round-trips to the server on every action. No JavaScript API calls. The server re-renders the full page and sends it back.

Generation 2 — ASP.NET MVC Razor + AngularJS (v1.x)

The core of TG.Web.UI. The server renders HTML via Razor (.cshtml). Inside these pages, legacy AngularJS (v1.x) adds client-side interactivity using ng- directives. The critical point: even the AngularJS templates are processed server-side first — the .NET Razor engine substitutes @GlobalResources variables before the HTML ever reaches the browser.

Server renders this .cshtml:
@GlobalResources.Label_searchJobs
→
Browser receives:
Search Jobs

Generation 3 — Angular 19 Custom Elements (Microfrontends)

The modern approach. Angular 19 components are compiled into standard Web Components and injected into Razor pages. They run entirely on the client and communicate with the backend via REST/JSON API calls — they do not participate in the Razor rendering pipeline at all.

Microfrontend Integration Mechanism

The Angular TG-Widgets project compiles to web components through a three-step process:

  • Bootstrap (main.web.ts / main.chatbot.ts): Uses Angular's createCustomElement() to wrap Angular components into web component wrappers.
  • Registration: The wrapped components are registered with the browser's custom element registry.
  • Consumption: Razor views load the compiled JS bundle and simply include the HTML tag <app-job-side-preview>.

Key Isolation Guarantee

Angular Custom Elements own their own DOM, styles (SCSS), state (RxJS), and API calls. They are completely isolated from the surrounding Razor page's JavaScript scope. No coupling to the MVC page lifecycle.

05Internationalization (i18n) Pipeline

Two Separate Pipelines for One Source of Truth

All translations originate from .resx resource files in TG.Web.UI. However, because the legacy and modern stacks run at different times (server vs. client), they consume these strings through completely different pipelines.

Pipeline 1 — Legacy MVC + AngularJS
  • Razor (.cshtml) evaluates .resx via auto-generated strongly-typed C# classes at render time
  • Syntax: @GlobalResources.Label_searchJobs in the .cshtml template
  • .NET replaces the variable with the translated string before sending HTML to the browser
  • Even AngularJS ng-template blocks are processed this way
  • No HTTP call for strings — they are baked into the HTML response
Pipeline 2 — Angular 19 Custom Elements
  • Angular runs entirely client-side — cannot use @GlobalResources Razor syntax
  • .resx strings are converted and synced to JSON files in assets/i18n/
  • On widget boot, @ngx-translate's TranslateHttpLoader fetches the correct JSON via HTTP
  • Angular components use the translate pipe
  • String loading is async — widgets display a loading state until the JSON is fetched

Single Source of Truth

The .resx files are the canonical source. The JSON files in assets/i18n/ are derived artifacts — they must be regenerated whenever .resx files change. If these get out of sync, the Angular widgets will show untranslated keys while the MVC pages show correct strings.

06Service-to-Service Communication (WCF & ASMX)

Cross-Process Service Calls

When TG.Core needs functionality from an external service, it crosses a process boundary. Two technologies handle this: WCF (Windows Communication Foundation) for newer integrations, and ASMX (legacy XML Web Services) for older ones. Both serialise C# objects to XML and send them over HTTP(S) or TCP.

WCF — Windows Communication Foundation

Used by TGWCFServices.sln. The calling side (TG.Core.Services) manages WCF connections through two key classes:

  • WcfServiceInvoker.cs — wraps service operation calls and handles WCF exceptions (FaultException<T>)
  • ChannelFactoryManager.cs — creates and caches ChannelFactory<TService> instances

ASMX — Legacy XML Web Services

Used by CandidateWebService.sln and SearchWebService.sln. Older than WCF; uses the Add Web Reference (WSDL) pattern to generate a typed proxy class. The calling pattern is similar to WCF but the proxy is a generated class rather than a ChannelFactory.

WCF — Key Characteristics
  • Supports multiple bindings: BasicHttpBinding, NetTcpBinding, WSHttpBinding
  • Uses [ServiceContract] / [OperationContract] attributes
  • Uses [DataContract] / [DataMember] attributes for serialisable types
  • ChannelFactory is cached and reused
ASMX — Key Characteristics
  • Older standard; WCF is the successor
  • Services are classes decorated with [WebService] attribute
  • Proxy generated at design-time from WSDL using 'Add Web Reference'
  • Always HTTP — no TCP or named pipe options
07Data Access Layer: ADO.NET & Entity Framework Exception

Primary Data Access — Raw ADO.NET

The main application deliberately avoids Entity Framework in favour of raw ADO.NET. This is a conscious legacy design decision, likely driven by performance requirements and the existing investment in stored procedures.

Component Role
DatabaseHelper.cs Central utility for creating SqlConnection, SqlCommand, executing stored procedures. Wraps ADO.NET boilerplate.
CommonDataUtil.cs Data hydration — maps raw SqlDataReader column values to C# entity properties. Acts as the manual ORM layer.
SessionRepository.cs Persists and retrieves user session state to/from SQL Server tables using the same ADO.NET pattern.
System.Data.SqlClient The .NET ADO.NET namespace. SqlConnection, SqlCommand, SqlDataReader, SqlParameter are the core types used throughout TG.Data.

The Entity Framework Exception — GatewayQuestionnaire

Entity Framework IS used — but only in the GatewayQuestionnaire module (GatewayQuestionnaire.sln). This module was built separately from the core application and uses EF 5.0.0 for its database interactions. The main TG.Data and TG.Core.Database layers do NOT use Entity Framework.

10Key Design Principles

Architectural Rules

These are the structural constraints that govern how the system is built and how it evolves. Understanding them is essential for safely modifying or extending any part of the codebase.

Strict Layer Ordering — No Skipping

  • The Presentation layer never calls TG.Data directly
  • The Data layer never contains business logic — that belongs in TG.Core
  • Dependencies always point downward: UI → Core → Data
  • Data always flows back up through each layer in reverse

Interface-Based Decoupling

  • TG.Services.Contracts defines C# interfaces for all services
  • Both in-process implementations and WCF proxies implement these interfaces
  • Callers are fully insulated from whether they call local code or a remote service
  • This is the seam that allows WCF services to be swapped or mocked in tests

Microfrontend Isolation

  • Angular Custom Elements own their DOM, styles, state, and API calls completely
  • They do not access the surrounding Razor page's JavaScript scope
  • The only interface is the HTML tag and its HTML attributes (input bindings)
  • Each widget can be upgraded or replaced independently of the host page

Module Separation at HTTP Boundary

  • GatewayQuestionnaire, WCF services, and ASMX services each live in separate solutions
  • They are never linked as C# project references from the main application
  • Integration happens only via HTTP redirects or SOAP/REST calls
  • Each module can be deployed, scaled, and versioned independently

ADO.NET Over ORM (Main App)

  • The main application deliberately uses raw ADO.NET — no Entity Framework
  • Stored procedures are the primary mechanism for complex queries
  • Manual mapping via CommonDataUtil.cs acts as a lightweight, explicit ORM
  • Exception: GatewayQuestionnaire uses EF 5.0 — isolated to its own solution
11Angular Architecture (TG-Widgets)

Overview

This document details the architecture of the modern frontend application built within the TG-Widgets project. The application utilizes modern Angular 19 features to provide interactive microfrontends.

1. Standalone Components

The project heavily relies on Standalone Components (a feature stabilized in Angular 15+).

  • No NgModules: Components like JobSidePreviewComponent, TgChatBotComponent, and JobsMapComponent are configured with standalone: true.
  • Direct Imports: Instead of declaring components in a shared module, standalone components import exactly what they need directly in their @Component({ imports: [...] }) metadata (e.g., importing CommonModule, MatDatepickerModule, or specific PrimeNG components).

2. Microfrontend Integration (Custom Elements)

The Angular application is not designed to run as a single page taking over the whole screen. Instead, it is configured to produce Web Components (Custom Elements) that can be individually dropped into legacy ASP.NET MVC Razor views.

  • Mechanism: It uses @angular/elements.
  • Bootstrapping: Inside main.web.ts and main.chatbot.ts, Angular uses bootstrapApplication instead of platformBrowserDynamic().
  • Element Creation:
    const jobSidePreviewElement = createCustomElement(JobSidePreviewComponent, { injector }); customElements.define('app-job-side-preview', jobSidePreviewElement);
  • Consumption: The legacy MVC backend simply renders <app-job-side-preview></app-job-side-preview>, and the browser's Custom Element Registry maps it to the Angular application logic.

3. Application State Management

The application avoids heavy third-party libraries like NgRx in favor of native Angular reactivity. It employs a two-pronged approach:

A. Angular Signals (Modern)

Global application state uses modern Angular Signals (signal<T>).

  • Example (AppStateService):
    private _state = signal<ScopeVariables>({ bLoggedIn: false, bJobCart: false, ... }); state = this._state.asReadonly(); updateVariable(key, value) { this._state.update(state => ({ ...state, [key]: value })); }
  • Components subscribe to appState.state() to re-render efficiently whenever global UI flags change.
B. BehaviorSubjects (RxJS)

For complex asynchronous data streams (like search queries and autocomplete filtering), the application utilizes BehaviorSubject from RxJS.

  • Examples: power-search-state.service.ts and autocomplete-state.service.ts use subjects to broadcast the latest API payload configurations across different widget instances.

4. Custom Directives

Directives are utilized to handle DOM manipulation, legacy UI parity, and accessibility features:

  • Accessibility: ng-enter.directive.ts and ng-space.directive.ts bind specific keyboard events (Enter/Space) to make custom UI controls fully accessible for screen readers.
  • UI Logic: click-to-toggle.directive.ts and prevent-defaultclick.directive.ts manage specific interaction behaviors without bloating component logic.
  • Autocomplete Extensions: Directives like ui-autocomplete-option and ui-autocomplete-dropdown are used to customize the behavior of the underlying PrimeNG autocomplete inputs.

5. Custom Pipes

Pipes are heavily used to format and sanitize data before it reaches the view, especially for rich-text job descriptions and translations:

  • Sanitization & Security: strip-html.pipe.ts, safe-html.pipe.ts, htmlencode.pipe.ts, and sanitize.pipe.ts ensure that strings coming from the backend or chatbot do not execute malicious scripts (XSS).
  • Formatting: truncate.pipe.ts is used to cleanly truncate long text strings with ellipses.
  • Translation: The application relies on the @ngx-translate pipe (| translate) to dynamically switch out text based on the loaded JSON dictionary.
